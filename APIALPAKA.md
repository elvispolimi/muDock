# Alpaka API Reference (muDock)

I created this file to serve as an encyclopedic list of all Alpaka APIs I analyzed during my porting from CUDA to Alpaka, explaining their syntax, purpose, usage status, and my rationale.

---

### `ALPAKA_FN_ACC`

- **Syntax:** `ALPAKA_FN_ACC auto function_name()`
- **Purpose:** Qualifies a function to be executable on the accelerator (emits `__device__` on CUDA, no-op on CPU).
- **Used:** Yes
- **Rationale:** I use this because it is mandatory for all mathematical and geometric helper functions (e.g., `rotate_molecule_alpaka`) that I called within my kernels.

### `ALPAKA_FN_HOST_ACC`

- **Syntax:** `ALPAKA_FN_HOST_ACC auto function_name()`
- **Purpose:** Qualifies a function for both host and device execution (`__host__ __device__`).
- **Used:** No
- **Rationale:** I didn't need to call any functions in the muDock codebase indiscriminately from both host and device scopes.

### `ALPAKA_NO_HOST_ACC_WARNING`

- **Syntax:** `ALPAKA_NO_HOST_ACC_WARNING`
- **Purpose:** Suppresses NVCC warnings regarding cross-domain host/device calls.
- **Used:** Yes (Implicitly)
- **Rationale:** This is automatically generated by Alpaka's functor templates, so I rely on it implicitly.

### `ALPAKA_UNROLL`

- **Syntax:** `ALPAKA_UNROLL(N)`
- **Purpose:** Provides a compile-time hint to unroll the subsequent loop (`#pragma unroll`).
- **Used:** Yes
- **Rationale:** I use this to maximize Instruction-Level Parallelism (ILP) on the GPU. I dynamically disable it on CPU backends to prevent breaking the compiler's auto-vectorization.

### `alpaka::getIdx`

- **Syntax:** `alpaka::getIdx<Scope1, Scope2>(acc)[dim]`
- **Purpose:** Returns the thread or block index (replaces `threadIdx.x` and `blockIdx.x`).
- **Used:** Yes
- **Rationale:** I use this because it's mandatory to calculate the global and local thread identifiers (e.g., `thread_id`).

### `alpaka::getWorkDiv`

- **Syntax:** `alpaka::getWorkDiv<Scope1, Scope2>(acc)[dim]`
- **Purpose:** Returns the grid or block dimensions (replaces `blockDim.x` and `gridDim.x`).
- **Used:** Yes
- **Rationale:** I use this to compute the stride dimension in my block-stride loops (`thread_per_block`).

### `alpaka::WorkDivMembers`

- **Syntax:** `alpaka::WorkDivMembers<dim, idx>{grid, block, elems}`
- **Purpose:** Struct encapsulating the execution hierarchy.
- **Used:** Yes
- **Rationale:** I use this because it is an architectural requirement of Alpaka to launch my tasks (used in `invoke_kernel_alpaka.hpp`).

### `alpaka::Vec`

- **Syntax:** `alpaka::Vec<dim, idx>{value}`
- **Purpose:** N-dimensional vector to define dimensions.
- **Used:** Yes
- **Rationale:** I use this as a base construct to define my 1D dimensions for the grid and blocks during my kernel launches.

### `alpaka::createTaskKernel`

- **Syntax:** `alpaka::createTaskKernel<acc>(work_div, F{}, args...)`
- **Purpose:** Instantiates the asynchronous task by associating the functor (kernel) with its parameters.
- **Used:** Yes
- **Rationale:** I use this to replace the native CUDA launch syntax `<<<grid, block>>>`.

### `alpaka::enqueue`

- **Syntax:** `alpaka::enqueue(queue, task)`
- **Purpose:** Submits the task into the hardware execution queue.
- **Used:** Yes
- **Rationale:** I use this because it is necessary to physically trigger my kernel execution.

### `alpaka::warp::shfl_down`

- **Syntax:** `alpaka::warp::shfl_down(acc, val, offset, width)`
- **Purpose:** Fetches the value of the variable `val` from the thread with a higher lane ID (replaces `__shfl_down_sync`).
- **Used:** Yes
- **Rationale:** This is a key element for my Warp Reduction. I use it to sum energy and centroids exponentially faster than using shared memory on the GPU.

### `alpaka::warp::shfl`

- **Syntax:** `alpaka::warp::shfl(acc, val, srcLane, width)`
- **Purpose:** Broadcasts a variable from a specific thread to all others in the warp (`__shfl_sync`).
- **Used:** Yes
- **Rationale:** I use this at the end of my warp reduction to propagate the final result from thread 0 to the other threads in the block.

### `alpaka::warp::shfl_up` & `alpaka::warp::shfl_xor`

- **Syntax:** `alpaka::warp::shfl_up(...)` / `alpaka::warp::shfl_xor(...)`
- **Purpose:** Alternative intra-warp data exchange variants.
- **Used:** No
- **Rationale:** I didn't use these because `shfl_down` is algorithmically sufficient for me to handle my standard iterative reductions (sum/min).

### `alpaka::warp::activemask`

- **Syntax:** `alpaka::warp::activemask(acc)`
- **Purpose:** Returns the bitmask of active threads in the warp (`__activemask()`).
- **Used:** No
- **Rationale:** I didn't need this because the parallelism of my muDock implementation ensures full participation of all threads (32) at my reduction points.

### `alpaka::warp::all` & `alpaka::warp::any`

- **Syntax:** `alpaka::warp::all(acc, pred)`
- **Purpose:** Evaluates a boolean predicate across the entire warp (Vote functions).
- **Used:** No
- **Rationale:** I didn't use these because my code has no warp-level conditional divergences that require voting mechanisms.

### `alpaka::syncBlockThreads`

- **Syntax:** `alpaka::syncBlockThreads(acc)`
- **Purpose:** Block barrier, suspending all threads until convergence (`__syncthreads()`).
- **Used:** Yes
- **Rationale:** I use this because it is crucial to prevent data races when I read or write to shared memory during CPU fallbacks or between my geometric computation steps.

### `ALPAKA_STATIC_ACC_MEM_CONSTANT`

- **Syntax:** `ALPAKA_STATIC_ACC_MEM_CONSTANT alpaka::DevGlobal<TAcc, Type> var;`
- **Purpose:** Allocates a variable in hardware constant memory (`__constant__`).
- **Used:** No
- **Rationale:** I simply overlooked this macro during the initial porting phase and failed to notice its existence in the framework.

### `alpaka::declareSharedVar`

- **Syntax:** `alpaka::declareSharedVar<T, UniqueId>(acc)`
- **Purpose:** Allocates a static array in block shared memory (`__shared__`).
- **Used:** No
- **Rationale:** I initially attempted to use it to cache atomic coordinates to force a constant-memory-like caching pattern. However, it proved detrimental (-8% performance) because the hardware L1 cache already handles these global reads perfectly, and the mandatory `alpaka::syncBlockThreads` barrier introduced heavy warp stalls. Furthermore, for warp reductions, I discovered that `alpaka::warp::shfl_down` automatically emulates shared-memory fallbacks on CPU, making manual `declareSharedVar` completely unnecessary.

### `alpaka::math::*` (sin, cos, sqrt, exp, abs, log)

- **Syntax:** `alpaka::math::sin(acc, val)`
- **Purpose:** Wrappers mapping math calls directly to hardware intrinsics.
- **Used:** Yes
- **Rationale:** I use these because standard C++ `std::` APIs cause implicit promotion to FP64 (`double`), which halves throughput on GPUs like the A100. Using `alpaka::math::` allows me to force fast native FP32 computations across all my backends.

### `alpaka::rand::Philox4x32x10`

- **Syntax:** `alpaka::rand::Philox4x32x10(seed, sequence, offset)`
- **Purpose:** Stateful, counter-based Pseudo-Random Number Generator (RNG).
- **Used:** Yes
- **Rationale:** I use this because it is the perfect replacement for `curandStatePhilox4_32_10_t`.

### `alpaka::atomic::*`

- **Syntax:** `alpaka::atomicAdd(acc, ptr, val)`
- **Purpose:** Executes thread-safe read-modify-write operations on global memory.
- **Used:** No
- **Rationale:** I avoided these because atomics cause heavy hardware serialization. My Warp Reduction pattern followed by a single global write (from thread 0) is much faster.

### `alpaka::block::shared::dyn`

- **Syntax:** `alpaka::block::shared::dyn(...)`
- **Purpose:** Shared memory allocated dynamically at runtime (like `extern __shared__`).
- **Used:** No
- **Rationale:** I avoided this because all shared memory sizes in my project depend solely on `BLOCK_SIZE`, which I fixed at compile-time to allow loop unrolling. Using static shared memory is sufficient for my needs.

---
*Disclaimer: While I strived to make this document comprehensive based on my muDock porting process, it is possible that I omitted some minor or implicit Alpaka APIs used internally by the framework.*
